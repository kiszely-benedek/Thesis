# ADR-0034 — A graph-tool agent, and why it does not need a tool per question type

## Context

The user's vision (2026-10-02): ingest the plant, then ask very many kinds of questions, fast and cheaply, like an
intelligent digital twin. The user wants an agent that calls graph tools tested, but objects: **it is not scalable if
every new question type needs a new tool.** CypherRAG (built) already lets an LLM write one free-form query; it is
the "free-form" end of the same idea. `qa-system.md` §18 T20 left Agentic as a could-item with four ad-hoc tools.

Two facts shape the choice. The schema has items with {tag, class-label chain, unit, sheet} and four directed
topology relations (`graph/schema.py`), so the space of topology questions is generated by a few graph operations.
And today a question's cost counts only the final call (`harness/runner.py`; design §2 F1), so an agent's cost would
be invisible without a harness fix (ADR-0035).

## Options considered

**A. No agent.** Nothing to build. Leaves the user's "digital twin API" untested, and leaves CypherRAG as the only
LLM-composed retrieval.

**B. One tool per question type** (isolation tool, path tool, count tool, …). Each tool is easy for the model, but
the tool set grows with the question set — the user's objection — and an evaluation on unseen types would really
test whether the right tool happened to exist.

**C. Six generic, composable primitives** over the resolver's plant graph — `find`, `neighbours`, `traverse` (with
stop and restriction filters), `path`, `filter`, `aggregate` — with result handles (`$r1`) so outputs feed inputs.
These are the standard graph-query operations over exactly the schema's vocabulary (select, expand, close, shortest
path, restrict, group). A new question type is a new composition. One filter language (`ItemFilter`: class label,
class, unit, sheet, tag) is shared by all six and uses the same label names CypherRAG's schema text lists.

**D. An agent whose only tool is free-form Cypher.** Maximal expressiveness, no API to design; the model must handle
off-page stubs and identity links itself. Kept as the **control** (`cypher_agent`), not as the main arm.

Sub-choice, protocol: **native tool calling** (OpenAI `tools` parameter) vs **plain JSON actions** in JSON mode.
Native calling may suit models trained for it; JSON actions need no client or cache-key change and behave the same
on every model the user wants to try.

## Decision

**C, with D built as the control, and plain JSON actions.**
1. `qa/plant_api/`: an item graph contracted from the resolver's occurrence graph (identity links merged, stub pairs
   contracted with a `via` record), six primitives, deterministic ordering, a compact text rendering, and
   `touched_keys` for evidence-node recall. The same primitives are the programs of ADR-0033's need labels.
2. `graph_agent`: a loop of at most 6 steps, observations capped at 4,000 characters, a cumulative prompt cap of
   150,000 characters, two consecutive errors stop it; its gathered observations go to the **shared final step**,
   so the answer step is identical to every other strategy's. Parameters are fixed by design, not tuned (tuning is
   paid at every point).
3. `cypher_agent` (should-tier): the same loop with one tool, `cypher(query)`, read-only, CypherRAG's limits.
4. `hier_agent`: the agent's first message carries a need-aware seed map (rules classifier, ADR-0033) capped at
   12,000 characters; it may stop at once or fetch more. The **cascade** (need-aware selection when the classifier is
   confident, else `graph_agent`) is computed offline from the two runs, with no extra call.
5. The API reports its own accuracy: item-graph fidelity against the gold plant (API-01) and a canonical primitive
   program per dev family whose accuracy against the reference functions measures coverage (API-02).

## Rationale

- The user's objection is answered structurally: the tool count is fixed by the schema, not by the question set, and
  held-out families (ADR-0035) test exactly that. A held-out family that no composition can express is reported as
  the API's boundary, not patched with a tool.
- `graph_agent` vs `cypher_agent` isolates typed-vs-free-form with iteration held equal; `cypher_agent` vs
  `cypher_rag` isolates iteration. Without the control, a better agent number could not be attributed.
- Plain JSON actions are the boring option: no change to `ChatClient`, its cache key or the fake transport; every
  call stays replayable (ADR-0014).

## Consequences

- Easy: one vocabulary serves Part 1, Part 2 and their combination; the demo application (ADR-0024) can show the
  agent's call trace as an explanation of an answer.
- Hard: agents make several calls per question, so latency and cost per question rise; the cost frontier
  (ADR-0035) is where that is weighed. The agent sees compact text while Hierarchical sees GraphML — a stated
  format confound.
- The primitives hide off-page connectors and identity links (they are the resolver's output); Cypher does not.
  That asymmetry is the hypothesis under test, stated in the thesis.
- **Revisit if** the dev pilot (QAR-P2) shows an invalid-action rate above 10 % (then native tool calling, as a
  follow-up ADR); `max_steps` stops more than 10 % of dev questions; or API-02 is below 1.0 on any dev family (the
  primitive set is then incomplete for known types, and the completeness argument is wrong).

**Accepted 2026-10-02 (user, in chat), with the main session's recommendations.** U1: 20 questions per family per corpus, **executed in stages** (10 first, extended to 20 only if the first half is informative); U2: the user topped up to $25 total — runs must be budgeted, staged and stopped early when results are clearly poor; U3: classifier pin glm-5.3-flash (logprobs per the 2026-10-02 snapshot); U4: QAR-T1 → T2–T5 (free) → J-tasks → T6–T9; U5: `cypher_agent` should-tier. The answer model is chosen in ADR-0019 from cheaper candidates, not assumed to be gpt-5-mini.
